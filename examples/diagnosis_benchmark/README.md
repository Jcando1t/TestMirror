# 诊断质量对照

在源码仓库根目录运行。每次指定一个新的可写输出目录。

```powershell
uv sync --locked
uv run --locked python -m examples.diagnosis_benchmark.run --out data/diagnosis-offline
uv run --locked python -m examples.diagnosis_benchmark.run --live --model deepseek-chat --out data/diagnosis-live
```

默认只跑离线诊断。使用 `--live` 时，脚本把自己生成的合成用例失败日志发送到官方 DeepSeek API。脚本读取已配置的 `DEEPSEEK_API_KEY` 或 `DEEP_SEEK_API_KEY`。

每个案例先运行一次失败版 pytest。两条诊断路径使用同一份输出，脚本校验规则提取的测试证据和客观指标一致。最后在临时项目应用预先定义的修复，复跑整组测试。`comparison.json` 记录原始日志指纹、诊断、已验证的修改、复跑计数及模型调用的提示词指纹、token 用量和耗时。

## 实测观察

2026-11-21 对同四份失败日志进行了对照。规则诊断在四例中都保留了出错位置和断言。模型建议由人工对照源码和复跑结果核实。

| 案例 | 模型给出的增量 | 核对结果 |
| --- | --- | --- |
| 免运费阈值 | 检查严格比较 `>`，条件成立时改为 `>=` | 已知修复后，三个边界用例全过。 |
| 跨调用状态残留 | 检查共享列表或可变默认参数 | 原因方向正确。模型还给出每次直接新建列表的建议，这会破坏显式传入列表的行为。 |
| 金额舍入 | 确认是否先转成了二进制浮点数，改用从原字符串构造的 Decimal，按 ROUND_HALF_UP 舍入 | 已知修复后，舍入边界和普通金额用例全过。 |
| 配置键读取 | 检查输入的 `max_items` 是否被忽略，保留缺失键时的默认值 | 日志足以定位要查的代码路径，具体的键拼写错误需查看实现确认。 |

改进分析提示词后，用完全相同的日志复测。模型在四例中都明确区分了已经观察到的结果和推测的实现细节。状态残留案例仍表明，仅凭失败日志给出的修法需要核对完整函数契约。把函数改为直接 `return [label]` 可以让原失败用例通过，但会令 `test_shared_list_when_supplied` 失败。将默认值改成 `None`、仅在未传列表时创建一个新列表，两条用例才都通过。

这四个案例用于检查诊断行为和复现具体误导。真实服务每次返回的文字可能变化，脚本验收的是测试证据、客观指标及已知修复，模型建议仍需结合源码核实。
